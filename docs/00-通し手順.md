# 通し手順（案件開始からリリースまで）

新しい案件 `anken-mockup` を例に、**ichiki を1から入れてリリースするまで**を順に並べる。  
各段に「打つコマンド」と「そのとき開く資料」を書いてある。詳細はその資料側にあるので、  
このファイルは**順番と、どこを見るか**だけを持つ。

> 個別の話は各ファイルにある。ここに書き写さない（2箇所に書くと必ず片方が古くなる）。

---

## 0. 前提を揃える

| 要るもの | 確認 |
|---|---|
| Node.js 22 以上 / npm | `node -v` |
| git | `git -v` |
| PHP（`php -l` の構文検査に使う） | `php -v` |
| [Local](https://localwp.com/)（WordPress をローカルで動かす） | アプリを入れる |

参照: [01-セットアップ.md](01-セットアップ.md)「事前に入れておくもの」「Local でサイトを用意する」

---

## 1. 案件のリポジトリを用意する

GitHub に `anken-mockup` を作り、手元に clone する。以降のコマンドは**すべて案件のルート**で打つ。

```bash
git clone https://github.com/<org>/anken-mockup.git
cd anken-mockup
```

> `.claude/ichiki` の中へ `cd` しないこと。相対パスが狂って、退避先の中にファイルを作る事故が起きる。

---

## 2. ichiki を入れる

```bash
git submodule add https://github.com/aifroide-jp/ichiki .claude/ichiki
git submodule update --init --recursive
node .claude/ichiki/bin/ichiki.js setup
```

`setup` が4つやる。

1. 依存を入れる
2. ブラウザ（Chromium）を入れる — 見た目比較とアクセシビリティ検査に使う
3. スラッシュコマンドを `.claude/commands/` へ配置する — Claude Code から `/setup` `/run` が使える
4. 案件設定とフィールド台帳を作る — **モックがまだ無ければ、ここは案内を出して正常終了する**

参照: [01-セットアップ.md](01-セットアップ.md)

---

## 3. Local でサイトを用意し、設定に書く

Local で新規サイトを作り、次の3つを控える。

| 値 | どこで分かるか |
|---|---|
| `wp_root` | Local がサイトを置くディレクトリ（例 `/Users/<自分>/Local Sites`） |
| `local_site_container` | `wp_root` 直下のこの案件のフォルダ名。**案件名と同じとは限らない** |
| `site_url` | Local が割り当てた URL（例 `http://localhost:10019`） |

**設定ファイルは2つある。混ぜない。**

| ファイル | 中身 | git |
|---|---|---|
| `.ichiki.json` | 案件の事実（`project` / `mockup` / `mockup_url` / `theme_slug` / `title_separator` / `retrofit` / `plugins_required`） | **コミットする** |
| `.ichiki.local.json` | そのPCの値（`wp_root` / `local_site_container` / `site_url`） | **コミットしない** |

上の3つは `.ichiki.local.json` に書く。`scan` は埋められない（人にしか分からない値）。  
読むときは前者に後者が上書きマージされるので、コマンド側は意識しなくてよい。

参照: [01-セットアップ.md](01-セットアップ.md)「設定は2つに分かれています」

---

## 4. `.gitignore` を置く

生成物とPC依存の設定を外す。**これを先にやらないと、検収成果物や個人のパスまでコミットに入る。**

```gitignore
.DS_Store
node_modules/

.ichiki.local.json

docs/検収/
docs/リリース手順書.md
docs/visual/
pa11y-report.json
visual-diff-report/
coverage.json
```

`docs/` 配下と `coverage.json` は `deliver` が決定的に作り直せるもので、  
中身に生成したPCのパスや実行時刻が入る。納品時は作り直して渡す。

確認: `node .claude/ichiki/bin/ichiki.js doctor` が `.ichiki.local.json` の無視漏れを見る。

## 5. モックを用意する

入口が2つある。**どちらに入るかで読む資料が変わる。**

### 5-A. 新規に書く

参照: [021-モックアップを作る.md](021-モックアップを作る.md)  
規約: [`rules/vocabulary.md`](../rules/vocabulary.md)（宣言 `data-*` の唯一の正）

### 5-B. 既存の HTML から作る（構造化）

見た目が合意済みで、宣言だけ無い HTML を受け取った場合。**見た目は1pxも変えない。**

```bash
mkdir -p .ichiki
git mv <ルートのページ一式> .ichiki/mockup-before/
```

そのうえで Claude Code に渡す。

```
.claude/ichiki/prompts/mockup-retrofit.md を読んで、その指示どおりに
.ichiki/mockup-before/ 以下の全ページを構造化してください。
```

参照: [022-既存htmlからモックアップを作る.md](022-既存htmlからモックアップを作る.md)

## 6. lint を通す

```bash
node .claude/ichiki/bin/ichiki.js lint .
```

**error 0 になるまで直す。** 指摘そのものが作業リストになる。  
`L20`（`data-acf` の無いテキスト＝更新対象外になる文言）は warn だが、  
**お客様と「これらは編集できません」の合意が要る**ので必ず読む。

参照: [023-AIに書かせてlintを通す.md](023-AIに書かせてlintを通す.md)

---

## 7. お客様に見せて合意する

渡し方は2つ。

```bash
# 検証サーバ等に配る
node .claude/ichiki/bin/ichiki.js publish-mockup <置き先>
```

GitHub Pages に出す場合は、GitHub の Settings → Pages で公開ブランチを指定する。  
公開したら、その URL を `.ichiki.json` に書く。

```json
"mockup_url": "https://<org>.github.io/anken-mockup/"
```

**これを書くと検収シートの「合意したデザイン」列がこの URL になり、  
リポジトリを持っていない人にも書類だけで渡せる。** 書かなければ相対パスに落ちる。

---

## 8. テーマを作る（gate）

```bash
node .claude/ichiki/bin/ichiki.js gate .
```

順に流れ、**最初に落ちたところで止まる**。

| 段 | 見るもの |
|---|---|
| ルール同期 | 規約と実装が揃っているか |
| lint | モックが規約どおりか |
| a11y | アクセシビリティ（**落ちても続行**。色の問題はデザインの判断） |
| scan | `acf-map.yaml` / `coverage.json` / `CLAUDE.md` を出す |
| 変換 | テーマを作る（台帳と突き合わせる） |
| フィールド突合 | 宣言したものがテンプレートに出力されているか |
| 構造忠実性 | モックの class が生成物から消えていないか |
| php -l | PHP の文法 |

**gate はテーマを一時ディレクトリに作るだけで、Local には置かない。**

参照: [03-変換して検査する.md](03-変換して検査する.md)

---

## 9. テーマを WordPress に入れる

```bash
node .claude/ichiki/bin/ichiki.js build
```

引数は要らない。`.ichiki.local.json` の `wp_root` + `local_site_container` と  
`.ichiki.json` の `theme_slug` から配置先が決まる。

そのあと **WordPress 側で3つ**。

1. 管理画面でテーマを有効化する
2. **管理画面を1回開く** — 固定ページ・投稿・メニュー・フォーム・サイト名が自動で作られる
3. 表示を確認する

参照: [03-変換して検査する.md](03-変換して検査する.md)「2. テーマを WordPress に入れる」

---

## 10. 検査して検収成果物を出す（deliver）

**動いている WordPress が要る。**

```bash
node .claude/ichiki/bin/ichiki.js deliver
```

順に流れる。前段の結果に後段が依存するので、順番は `deliver` が守る。

| 段 | 内容 |
|---|---|
| 公開後の検証 | 宣言どおりに出ているか（`verify:live`） |
| 見た目の比較 | モック ↔ 実サイト（数分。`--no-visual` で飛ばせるが C1 の表示確認が「未実行」になる） |
| アクセシビリティ | `a11y --site` |
| 検収成果物 | C1 / C3 / ガイド |
| リリース手順書 | `docs/リリース手順書.md` |

出るもの。

| ファイル | 誰が使うか |
|---|---|
| `docs/検収/l1-checklist.tsv` | 社内スタッフ。目で見て判定を書き込む |
| `docs/検収/l1-guide.md` / `.html` | 同上。使い方（画像は埋め込み済みで単体で開ける） |
| `docs/検収/test-spec.md` | 開発。自動判定を含む全記録 |
| `docs/リリース手順書.md` | 本番へ載せる人 |

---

## 11. 検収してもらう

`docs/検収/` を社内スタッフに渡す。渡す前に、シートの2列の性質を理解しておく。

| 列 | 渡された人が開けるか |
|---|---|
| 合意したデザイン | `mockup_url` があれば**そのまま開ける**。無ければリポジトリが手元に要る |
| 実際のページ | `site_url` が Local なら、**その人は自分の Local のポートに読み替える**（ガイドに明記される） |

共有できる検証サイトがあるなら、そのURLで回し直すと読み替えが要らない。

```bash
node .claude/ichiki/bin/ichiki.js deliver https://staging.example.com
```

## 12. 構造化の後始末（5-B から来た場合だけ）

全ページ構造化し終わったら、宣言を消す。**消し忘れると未解決リンクが警告のまま許され続ける。**

```bash
node .claude/ichiki/bin/ichiki.js retrofit:done
```

案件のファイルを触るところまでを一度にやる。

1. `.ichiki/mockup-before/` がコミット済みか確認する（未コミットなら止まる。消すと戻せないため）
2. `.ichiki.json` から `retrofit` 節を消す
3. `.ichiki/mockup-before/` を消す
4. `gate` を回す ← **未解決リンクが error に戻った状態で通るかを、その場で確かめる**

そのあと **WordPress 側を触る2つは案内だけ**で、自動では走らない。

```bash
node .claude/ichiki/bin/ichiki.js build     # 配置済みテーマの「変換途中です」通知が消える
# 管理画面を1回開く
node .claude/ichiki/bin/ichiki.js deliver   # 検収成果物とリリース手順書の但し書きが消える
```

**`retrofit` を消すと未解決リンクが警告から error に戻る**ので、消したあとに `gate` を
通して初めて本当の合格が分かる。配置済みのテーマとリリース手順書には「構造化が途中」の
表示が残っているため、作り直しまでが後始末になる。

`doctor` は宣言が残っている間ずっと言うので、やり忘れには気づける。

参照: [022-既存htmlからモックアップを作る.md](022-既存htmlからモックアップを作る.md)「3. 途中であることを宣言する」

## 13. 本番へ出す

`docs/リリース手順書.md` に、この案件のページ・フォーム・メニューの一覧込みで手順が出ている。  
テーマの持ち出しは All-in-One WP Migration 等、案件の運用に従う。

```bash
# 単体で作り直したいとき
node .claude/ichiki/bin/ichiki.js release
```

## ichiki を新しくするとき

```bash
git -C .claude/ichiki fetch
git -C .claude/ichiki checkout origin/main
node .claude/ichiki/bin/ichiki.js setup
```

`git submodule update` は**更新コマンドではない**（親が記録したコミットへ揃えるもの）。  
`setup` を流し直すのは、`.claude/commands/` のコピーを更新するため。

参照: [01-セットアップ.md](01-セットアップ.md)「更新するとき」

## 困ったとき

| 症状 | 見るところ |
|---|---|
| コマンドが動かない・設定が無い | `node .claude/ichiki/bin/ichiki.js doctor` |
| lint が大量に落ちる | [023-AIに書かせてlintを通す.md](023-AIに書かせてlintを通す.md) |
| gate が止まる | 出力に「どのファイルの何行目が、なぜ駄目か」が出る |
| deliver がサイトに繋がらない | `.ichiki.local.json` の `site_url`。Local はポートが変わる |
| 宣言の書き方が分からない | [`rules/vocabulary.md`](../rules/vocabulary.md) |
