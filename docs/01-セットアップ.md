# Ichiki を使えるようにする

> [案件のトップに戻る](../../../README.md)（やりたいことから探せます）

案件のリポジトリで **1回だけ**やる作業です。終われば、あとはコマンドを叩くだけになります。

---

## 事前に入れておくもの（Mac / Windows 共通。この2つだけ）

| | 何のため | 入手先 |
|---|---|---|
| Node.js 24+ | Ichiki 自体の実行（node で書かれている） | [node LTS版](https://nodejs.org/ja) |
| Local | WordPress の開発環境。サイト起動と PHP をこれ1つでまかなう | [Local](https://localwp.com/) |

入ったかどうかは、ターミナルでこれを打てば分かります。バージョン番号が出れば OK です。

```bash
node -v
git --version
```

`git` は既に入っている前提ですが、無ければ下のセットアップコマンドが入れ方を案内して止まります。

**PHP と wp-cli は別途入れる必要はありません。** PHP は Local に同梱されているものを  
Ichiki が自動で借ります。wp-cli も無くて構いません（初期データは管理画面を1回  
開けば入ります。無い場合の代わりの手段は、下の `setup` を実行したときに案内が出ます）。

## Local でサイトを用意する

Ichiki のセットアップの前に、この案件用の WordPress サイトを Local に作っておきます。

（**これは Ichiki の作業ではありません。** Local 側の準備です）

1. Local を開き、**サイトを新規作成**します。

   コンテナ名を決めます。案件名と同じでなくて構いません。

2. PHP・Webサーバー・データベースを選び、WordPress 環境を作ります。

   **次のバージョンを指定してください**（WordPress の要件から逆算した組み合わせ。  
   Local の既定とは限らないので、選択肢から明示的に選ぶこと）。

   - PHP 8.5.x
   - Apache 2.4.x
   - MySQL 8.4.0

   選択肢に無い等で完全に一致しなければ、一番近いバージョンで構いません。  
   その後、IDとパスワードを入力しますが、任意で構いません。

3. 作ったサイトを右クリック →「**Site folder**」（または「Go to site folder」）を選びます。

   **そのサイト自身のルートフォルダ**（`app/` `conf/` `logs/` 等が並ぶ階層。  
   `app/public` の1つ上）が Finder / エクスプローラーで開きます。

   アドレスバーのパスをコピーしてください。下の「やること」で使います。

   例えば開いたパスが Mac で `/Users/…/Local Sites/mysite`、  
   Windows で `C:/Users/…/Local Sites/mysite` なら  
   （Windows は `\` ではなく `/` に置き換えて控えてください。  
   後述の理由により `\` のままだと壊れます）:

   | この案件が使う値 | 値 |
   |---|---|
   | `wp_root` | `.../Local Sites`（サイト名より上の部分） |
   | `local_site_container` | `mysite`（そのフォルダ自身の名前） |

`site_url` は Local が自動で決めます。**基本は変えなくて構いません。**  
手元の環境でポートが競合していたら、Local 側でポートを確認してから書き換えてください。

## やること

**前提: 案件のリポジトリは、この時点で既に手元にある**ものとします  
（アクセス権をもらって `git clone` 済み、または新しく作った）。  
リポジトリの入手方法自体は案件ごとに違うので、ここでは扱いません。

```bash
# 0. 案件のリポジトリのルートに移動する
cd <案件のリポジトリ>
```

ここから先は、**このプロジェクトに Ichiki を入れるのが自分が初めてか**で変わります。

**初めて入れる人（自分がこの案件に Ichiki を導入する）**

```bash
git submodule add https://github.com/aifroide-jp/ichiki .claude/ichiki
git submodule update --init --recursive
```

**既に Ichiki が入っている案件に参加する人（clone しただけ）**

`git submodule add` は**打ちません**。もう `.gitmodules` に登録済みなので、  
打つと `already exists in the index` のようなエラーになります。  
代わりにこちらだけです。

```bash
git submodule update --init --recursive
```

（`git clone --recurse-submodules <リポジトリURL>` で最初から clone していれば、  
この工程自体が要りません）

**ここから共通**

```bash
node .claude/ichiki/bin/ichiki.js setup
```

依存のインストールと、見た目比較に使う Chromium のダウンロードが走ります。  
**初回は数分かかります。** 固まったように見えても、そのまま待ってください。

**モックがまだ無いプロジェクトでは、ここで止まって正常終了します。**  
依存・ブラウザ・コマンド配置までは済んだうえで、新規に書くなら  
[021-モックアップを作る.md](021-モックアップを作る.md)、既存の合意デザインが  
あるなら[022-既存htmlからモックアップを作る.md](022-既存htmlからモックアップを作る.md)  
への案内が出ます。**これはエラーではありません。** モックを用意してから、  
もう一度このコマンドを流せば、下の対話（`.ichiki.json` の入力）と `doctor` まで続きます。

**モックが既にある場合は続けて、このコマンドの途中で `.ichiki.json` の3つを聞かれます。** 上で控えた値をそのまま  
答えてください。Enter で候補（Local から自動検出したもの）をそのまま使えます。  
`wp_root` / `local_site_container` / `site_url` は**この案件を動かす環境ごとに違う値**  
（あなたの Local のどこにサイトを作ったか）なので、機械では決められず、ここだけ人に聞きます。

聞かれなかった（CI・スクリプト経由など、対話できない環境で実行した場合）ときは、  
`.ichiki.json` を直接編集してください。**通常のターミナルで打っていれば必ず聞かれます。**

```jsonc
"wp_root": "/Users/…/Local Sites",
"local_site_container": "mysite",
"site_url": "http://localhost:10000"
```

> **手で編集するときは、Windows のパスを `/`（フォワードスラッシュ）で書いてください。**  
> `C:\Users\…\Local Sites` のように `\` を1つで書くと、JSON では `\t` `\n` の  
> ような制御文字として解釈されます。パースが失敗すればまだ気づけますが、  
> `\t` `\n` `\r` は**パースが通ってしまい、値が静かに壊れます**  
> （実測: `C:\temp\newsite` が読み込むとタブ文字・改行文字を含む壊れた  
> パスになっていた）。`C:/Users/…/Local Sites` のように書けば動きます。  
> 対話で答えたときはこの心配はありません（自動でエスケープされます）。

終わったかどうかは、これで分かります。

```bash
node .claude/ichiki/bin/ichiki.js doctor
```

`問題ありません。` と出れば終わりです。出ない項目には直し方が書いてあります。  
**手元の道具（node / npm / git / php / wp-cli）とサイトに繋がるかも見ます。**

上のコマンドは何度流しても既存のファイルを壊しません。更新のときも同じものを流せます。

## 詰まったとき

### `node が古すぎます` と言われた

24 以上に上げてください。WordPress 側の制約ではなく、Ichiki 自体  
（node で書かれている）だけの話です。

**nodejs.org のインストーラで入れた人（前提）**

1. https://nodejs.org/ja を開く
2. LTS版（24.x）のインストーラをダウンロード
3. 実行する（Mac: `.pkg` / Windows: `.msi`）。既存のバージョンは自動で上書きされる
4. **ターミナルを開き直して** `node -v` で確認する  
   （開いたままのターミナルには PATH の更新が反映されない）

<details><summary>nvm / Homebrew で入れている人（Herd 経由の nvm も含む）</summary>

`which node` の場所が `nodejs.org` のインストーラでも Homebrew でもなく、  
Herd（PHP/Laravel 用のローカル開発ツール）が用意した `nvm` を経由している  
こともあります（実測: `~/Library/Application Support/Herd/config/nvm/...`）。  
その場合も `nvm` コマンド自体は普通に使えるので、下と同じ手順で動きます。

```bash
# nvm（nvm-windows も、Herd 同梱の nvm も同じコマンド）
nvm install 24
nvm use 24
nvm alias default 24   # 新しいターミナルでも既定を24にする

# Homebrew（Mac）
brew upgrade node
```

</details>

### `セットアップが終わっていません` / `Cannot find module 'cheerio'` が出た

依存が入っていません。**案件のルートで**セットアップを流し直してください。  
依存も、見た目の比較に使う chromium も、これ一つで入ります（初回は数分）。

```bash
node .claude/ichiki/bin/setup.js
```

**「やること」で打った `node .claude/ichiki/bin/ichiki.js setup` と同じものです。**  
`bin/setup.js` を直接呼んでも、`bin/ichiki.js` の `setup` サブコマンド経由で呼んでも  
中身は同じスクリプトです（呼び方が2通りあるだけ）。

### `Cannot find module '...\.claude\ichiki\.claude\ichiki\bin\ichiki.js'`

パスが二重になっています。**`.claude/ichiki` の中にいます。**  
コマンドは案件のルートで叩きます。

```bash
cd <案件のルート>
node .claude/ichiki/bin/ichiki.js doctor
```

`.claude/ichiki` の中で叩くと Ichiki 自身のファイルを読んでしまうため、  
気づかずに進めないよう Ichiki 側で止めています。

### `.claude/ichiki` の中が空

submodule が取り込まれていません。

```bash
git submodule update --init --recursive
```

クローンするときに `--recurse-submodules` を付けると、これが要らなくなります。

### `.ichiki.json` が無い / `モックの場所が分かりません` と出る

**通常は「やること」の `setup` が内部で `scan` を呼ぶので、ここは通りません。**  
`setup` を経由せず `lint` 等の他のコマンドを先に叩いた場合や、`.ichiki.json` を  
消してしまった場合に、このエラーが単独で出ます。案件の設定がまだ作られていません。  
`scan` を1回回すと作られます。引数は省略でき、既定でリポジトリのルートを見ます。

```bash
node .claude/ichiki/bin/ichiki.js scan
```

`wp_root` / `local_site_container` / `site_url` は**あなたの環境の値**なので空で出ます。  
[上の「Local でサイトを用意する」](#local-でサイトを用意する)で控えた値を書き足してください。

```jsonc
"wp_root": "/Users/…/Local Sites",
"local_site_container": "mysite",
"site_url": "http://localhost:10000"
```

Windows のパスは `/` で書いてください（`\` を1つで書くと壊れます。上の「やること」参照）。

`.ichiki.json` は git に入りません（人によって値が違うため）。  
**クローンした人がそれぞれ作ります。**

### スラッシュコマンドが古い動きをする

`.claude/commands/` へのコピーをやり直していません。

```bash
cp .claude/ichiki/commands/*.md .claude/commands/
```

（PowerShell でも `cp` は `Copy-Item` のエイリアスとしてそのまま動きます）

Claude Code は `.claude/commands/` しか見ないので、本体を更新してもコピーし直さないと  
古い手順が動き続けます。`doctor` がこのズレを見ています。

### `gate` が `lint` で大量に落ちる

モックでないディレクトリを読んでいることがあります。`.ichiki.json` に足してください。

```jsonc
"not_mockup": ["docs", "scripts", "参考資料"]
```

既定で `docs` と `scripts` は外れています。隠しディレクトリと `node_modules` も外れます。

## 更新するとき

submodule を進めてから、**初回と同じセットアップコマンドを流す**だけです。

```bash
cd .claude/ichiki
git fetch
git checkout origin/main
cd ../..
node .claude/ichiki/bin/ichiki.js setup
```

`git checkout origin/main` は **detached HEAD** という状態になりますが、意図した  
動作です（submodule はブランチではなく特定のコミットを指す運用のため）。  
`You are in 'detached HEAD' state` と表示されても壊れていません。

既存のファイルを壊さないので、初回と同じものを流せます。  
`.claude/commands/` のコピーもやり直されます（**忘れると古い手順が動き続けます**）。

`.ichiki.json` の `ichiki_version` も自動で揃います。  
やり直したかどうかは `doctor` が見ています。
