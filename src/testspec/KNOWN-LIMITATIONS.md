## ② 自動チェックの正しさ（構造的な限界）

自動チェックは「壊れていないことの一部証拠」であって「正しく動いていることの証明」ではない。特に以下は自動OKでもすり抜ける可能性がある。

- **ACF差し替え**: デフォルト値の文字列がHTMLに出現するかだけを見ている。ACFフィールドとして正しく紐付いていても、PHPにベタ書きされた同じ文字列でも、どちらも自動OKになる（管理画面で値を変えても反映されない壊れたページを検出できない）
- **リンク遷移**: リンク先が生存している（非404）かだけを見ている。行き先が意図した別のページを指す配線ミス（生きているが宛先が違う）は検出できない
- **フォーム送信**: `wpcf7-form` のタグ出力だけを見ている。フィールド数・種類の一致や、実際の送信成立・メール着信は確認していない（着信確認はC3で人手に委ねている）
- **アクセシビリティ簡易チェック**: 2026-08-05時点では `pa11y-report.json` が一度も生成されておらず実質ノーカバレッジだったが、2026-08-06に解消。pa11y-ci導入・`.ichiki.json` の `site_url` 修正（`http://nature-kitakyushu.local` が実体と合っておらず全ページ接続失敗していた）・`a11y.js` のパースバグ修正（pa11y-ci実際の出力形式 `results: { url: issues[] }` に未対応だった）・接続失敗を違反件数として誤カウントしない対策（`code` を持たないエントリが混ざったら例外を投げて落とす）を行い、実データで204件のaxe-core違反を検出できる状態にした。ただし残課題2点: ①検出した204件自体はまだ1件も直していない、②rules/ichiki.mdが本来求めるGitHub Actions連携（AA違反時にPRマージブロック）は未着手でローカル手動実行のみ

これらのうち実害に直結しやすい優先度: リンク遷移の宛先違い ＞ アクセシビリティで検出した204件の違反が未修正 ＞ ACF差し替えのベタ書き誤検知（お手本に忠実な実装であれば起こりにくいため）。

## ③ 実装の移植性（他Ichiki案件で使い回す場合の注意）

- CPT判定・グルーピングは `inc/seed-posts.php` の `$pages` 配列と `nkk_seed_post()` 呼び出しを正規表現でパースして行っている。この配列名・関数名は rules/ichiki.md の固定契約ではなく、本案件のPhase1実装がたまたまその形だっただけ。他案件で書き方が違えば、パースは黙って空配列を返し、ページ種別判定が崩れる（クラッシュはしないが誤判定になる）
- `lib/checks/visual-diff.js` は `ichiki diff` が出すレポートの形式に依存。無い場合は全ページ「visual-diff未実行」として安全に縮退する（比較対象の一覧はかつて `scripts/visual-diff/pages.js` に手書きしていたが、案件側の JSON に移した）
- `.ichiki.json` の `site_url` はLocal環境の実体とズレやすい（2026-08-06に実際に発生）。Localは `.local` ドメインとサイト固有の直接ポート（例: `http://localhost:10004`）を両方割り当てるが、`.local` ドメインがLocal側のルーターに正しく登録されていないと接続失敗になる。`site_url` を設定・変更する時は、対象URLに実際にHTTPで疎通できる（かつ`wp-json`のリンクヘッダーがそのURLで返る＝WordPress自身の`siteurl`と一致している）ことを毎回確認すること

## 根本原因メモ

acf-map.yaml（Phase0 scan出力）はページごとのDOM構造しか持たず、「このN件は同じCPT詳細テンプレートを共有する」という構造的な繰り返しパターン情報を持たない。セクション名もモックアップのCSSクラス名（`section_white`/`section_gray`等）由来で、意味的な構造ではない。モックアップ側でCPT候補となる詳細ページ群のセクション構造・id命名を統一しておけば、Phase0のscanの時点で繰り返しパターンを機械的に検出でき、Phase2のテスト範囲決定はもっと単純になる（詳細はメモリー `feedback_ichiki_mockup_structural_consistency` 参照）。

## 実データで見つかった既存の不具合（今回は未対応。C1の「⚠ 要確認」および本文中の自動NG行に記録済み）

- `events/sample.html`（平尾台シャボン玉フェスティバル）に対応する投稿が `seed-posts.php` に無い
- 多くのページでACFフィールドの大半がフロントに出力されていない（例: `活動ブログ` 2/14一致、`活動拠点` 22/34一致）

## 改善案（2026-08-06検討・未着手）

### 現状把握: acf-map.yamlが「AI向け参考資料」止まりになっている

`.claude/ichiki/commands/run.md`（Phase1の指示書）を確認すると、`inc/acf-<slug>.php`（ACFフィールド登録）も `single-<cpt>.php` 等（フィールド出力）も、すべてClaude Codeが acf-map.yaml と固定ルール・お手本を読んで**自由記述でPHPを書く**前提になっている。acf-map.yaml は field_name・type・default値まで機械可読で持っているにもかかわらず、それを直接消費してPHPを生成するスクリプトは存在しない。

検収ゲート（`.claude/ichiki/bin/gate.js` の `check-coverage`）も、acf-map.yamlの全フィールドが `field-map.json`（命名対応表）に載っているか、つまり「ACFとして登録し忘れていないか」しか見ていない。「登録した値が実際にテンプレートへ出力されているか」を見るチェックはどこにも無い。これが「実データで見つかった既存の不具合」（活動ブログ2/14一致、活動拠点22/34一致など）を生み、かつ誰にも検出されなかった直接の要因と考えられる。

### 途中で疑った「根本原因メモ」（モックアップの構造不統一）の検証結果

当初は上記の不具合の原因として、「根本原因メモ」に書かれているモックアップのセクション構造不統一を疑った。`about/spots/*.html`（9件）・`center/*.html`（10件）・`events/*.html` のイベント詳細候補（7件）・`network/cases/*.html`（2件）のセクション構造・class名を比較したところ、CPT候補として実際に使われている4グループはいずれも内部的に完全統一されていた。ここだけ見ると「モックアップは綺麗に揃っているので根本原因メモの仮説は外れ」と結論しかけたが、それは早計だった。

範囲を全ページに広げたところ、`section--white` / `section--gray` / `cta-band` というクラス語彙は、CPT候補グループだけでなく `join/index.html`・`about/strategy.html`・`network/index.html` のような**単発の固定ページにも同じ語彙で使われている**ことがわかった（セクション数・順序はそれぞれ異なる）。つまり:

- クラス名の一致だけを見る構造検出では、単発ページとCPTグループを取り違えるリスクがある
- 実際にCPTグループを区別できているのは「セクション数＋順序の完全一致が2件以上ある」という、クラス名一致より厳しい条件によってであり、これが機械的に検出できる保証はモックアップの綺麗さとは別問題である
- `nkk_photo`・`nkk_network` はseed投稿が1件しかなく比較対象が存在しないため、この方法では**原理的に検出不可能**（モックアップがどれだけ統一されていても解決しない）

したがって結論を訂正する: モックアップの構造は乱れていなかったが、それだけでは「根本原因メモ」が指摘するCPTグルーピングの機械検出問題は解消しない。根本原因メモの主張はむしろ補強される（ただし当初の想定とは異なる理由で: 「構造が汚い」ではなく「レイアウト語彙がグループ内外で共用されており、多インスタンス比較が前提の検出手法は単発ページとの誤判定リスクと1件のみのCPTへの原理的な対応不能を抱えている」）。フィールド出力漏れ自体（活動ブログ2/14一致等）は、CPTグルーピング問題とは別軸で、Phase1が「CSSが複雑だった」「全ページ一括で片付けようとした」ことによる単純な実装漏れである可能性が高い。

### 改善の方向性: Phase1を「機械生成でよい部分」と「AI判断が必要な部分」に分割する

- **機械生成に切り替え可能（スクリプトのみ・AI不要）**:
  - ACFフィールド登録（`inc/acf-<slug>.php`）: acf-map.yamlのfield_name / type / defaultから `acf_add_local_field_group()` 呼び出しを直接生成できる
  - フィールド出力（テンプレート内の `get_field()` / `the_field()` 呼び出し）: mockupの生HTMLに実際に存在するdefault値の文字列を検索し、`<?php the_field('field_name'); ?>` へ機械的に置換して生成する。置換元の文字列が見つからない場合はその場でスクリプトがエラーを出すため、「登録したのに出力し忘れる」というバグ自体が構造的に発生しなくなる
- **引き続きAI／人の判断が必要な部分**: CPT/固定ページの判定、型が曖昧なケース（wysiwyg/textarea/url）、意味ベースのフィールド命名、nav→カスタムメニュー変換、form→CF7変換、hide_on_screenの判断、CPTの一覧・詳細ロジック
